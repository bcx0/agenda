# Agenda : RDV réguliers, créneaux fantômes et « Ajouter un créneau » (25/11/2026)

Branche : `fix/agenda-recurrences-2026-11`, partie de `main` 83194b4 (version en production).

## 1. Causes exactes

1. **Aucune exception possible sur une série.** Un « RDV régulier » (`RecurringBlock`) bloque son créneau chaque semaine, sans date de fin ni exception par date. Pour une série liée à un client, l'app crée en plus une réservation par semaine, mais ces réservations n'étaient pas reliées à la série.
2. **Déplacer une occurrence laissait l'ancien créneau bloqué.** La réservation était bien déplacée (dans l'admin, par le client ou dans Google), mais le `RecurringBlock` continuait de bloquer la date d'origine. C'est le bloc récurrent All-in 21:00-22:00 (Bruxelles) resté affiché le 15/02.
3. **« Ajouter un créneau » échouait en silence.** L'action crée une ouverture du jour (exception `OPEN`), qui ne neutralise jamais un bloc récurrent, puis répond quand même « Disponibilité du jour enregistrée ».
4. **Deux calculs de disponibilité différents.** `getAvailability()` (ce que voient l'admin et les clients) et `checkSlotAvailability()` (ce que le serveur accepte) avaient chacun leur propre logique. Ils divergeaient à la frontière des périodes Belgique et quand une ouverture du jour existait.
5. **Synchronisation déclarée réussie sans l'être.**
   - Le jeton de synchro Google avançait même si un événement était en erreur : le changement concerné était perdu.
   - La mise à jour Google d'un RDV déplacé n'était pas attendue (coupée par Vercel après la réponse), et rien ne la retentait.
   - Une vieille version Google pouvait écraser un déplacement local pas encore poussé.
   - Supprimer dans l'app un bloc venu de Google effaçait la ligne même si la suppression Google échouait : le bloc réapparaissait à la synchro suivante.
6. **Fuite d'information.** La cause d'un blocage, qui peut contenir le nom d'un autre client, était envoyée avec chaque créneau à la page de réservation client.

Reproduit avec le code de production sur une base isolée : après le déplacement du 15/02 au 24/02, le 15/02 21h reste bloqué par le bloc All-in. « Ajouter un créneau » répond « Disponibilité enregistrée » sans rien débloquer.

## 2. Corrections

- **Moteur de disponibilité unique** (`lib/availability-engine.mjs`, pur et testé). L'affichage admin, la page client, la réservation, la reprogrammation et les actions admin utilisent les mêmes fonctions sur les mêmes données (`lib/availability-data.mjs`). Ordre de priorité :
  1. réservation réelle ;
  2. indisponibilité explicite (blocage manuel, événement Google) ;
  3. exception d'occurrence ;
  4. règle récurrente ;
  5. horaires habituels.
- **Exceptions d'occurrence et période de série.**
  - Nouvelle table `RecurringBlockException` : `SKIP` (occurrence libérée) ou `MOVE` (occurrence déplacée). Une seule exception par occurrence, écritures idempotentes.
  - Colonnes `startDate` et `endDate` sur `RecurringBlock`.
- **Lien réservation → série** (`Booking.recurringBlockId`, `occurrenceDate`). Quand un RDV de série est déplacé ou annulé, d'où que ce soit (admin, client, Google), son créneau d'origine se libère automatiquement. Aucun déclencheur n'est nécessaire.
- **Trois modes de modification** : cette occurrence, cette occurrence et les suivantes (la série est scindée), toute la série. Les RDV réservés suivent le nouveau motif en tout ou rien : la modification est refusée si l'un d'eux tombe sur une autre réservation. Même chose pour la suppression.
- **« Ajouter un créneau » réparé.**
  - Sur un bloc récurrent : l'occurrence de CETTE date est libérée.
  - Hors horaires : l'ouverture est fusionnée avec le reste du jour.
  - Sur une réservation ou une indisponibilité explicite : refus avec un message clair.
  - Le résultat est revérifié avant validation : rien ne « réussit » sans effet.
- **Concurrence.** Un verrou applicatif (`pg_advisory_xact_lock`) est pris par les actions admin, les réservations et les reprogrammations, et la disponibilité est revérifiée dans la transaction.
- **Synchronisation.**
  - Le jeton n'avance que si tout a été traité (sinon `sync_partial`, qui compte comme une panne pour les alertes).
  - Les RDV déplacés passent en `pending`. Le push est attendu et, en cas d'échec, retenté à chaque cron (`retryPendingUpdates`).
  - Une modification locale plus récente n'est jamais écrasée par une version Google plus ancienne.
  - La re-création Google est idempotente : un événement déjà créé est rattaché, pas dupliqué.
  - Un bloc n'est supprimé localement que si Google l'a vraiment supprimé.
- **Cache.** Le cache routeur côté navigateur est à 0 s pour les pages dynamiques (`staleTimes.dynamic`). Chaque action admin rafraîchit l'agenda, `/book` et `/manage`.
- **Admin.** Pour chaque créneau bloqué, l'écran affiche :
  - toutes les causes, avec leur type (Réservation, Récurrence, Indisponibilité manuelle, Calendrier Google) ;
  - l'action adaptée : libérer cette date, lever, voir le RDV, gérer la série ;
  - les occurrences libérées ou déplacées du jour, avec « Rebloquer cette date ».

  L'onglet RDV réguliers montre les prochaines occurrences avec leur état, et permet de déplacer, supprimer ou borner une série. Chaque action affiche sa confirmation ou la raison du refus.
- **Données existantes.**
  - La migration lie automatiquement les seules réservations qui tombent exactement sur le motif d'une seule série.
  - `scripts/reconcile-recurring-ghosts.mjs` est en lecture seule par défaut. Il liste les fantômes prouvés (RDV annulé à l'horaire exact), les fantômes probables (RDV déplacé, à valider) et les « Ajouter un créneau » restés sans effet. Il n'applique que des liens ou des exceptions, sur ordre explicite.
  - `scripts/diagnostic-recurrences.sql` sert de diagnostic SQL en lecture seule.

## 5. Mise en production

1. Lancer `scripts/diagnostic-recurrences.sql` dans l'éditeur SQL Supabase (lecture seule) pour voir les données réelles d'All-in.
2. Appliquer `prisma/migrations/20261125120000_recurring_occurrence_exceptions/migration.sql` dans Supabase **avant** de déployer le code (le code lit les nouvelles colonnes).
3. Fusionner la branche dans `main`. Vercel déploie.
4. `node scripts/reconcile-recurring-ghosts.mjs` (lecture seule), puis, après validation : `--apply-verified` et, au cas par cas, `--link` ou `--release`.
5. Dans l'admin, sur la série All-in : borner la période et rebloquer ou libérer le 15/02 selon la réponse de Geoffrey.

Retour arrière : revenir au commit précédent, puis exécuter `down.sql` (cela supprime les exceptions saisies entre-temps : les exporter avant).

## 6. Limites restantes

- Les données de production n'ont pas pu être lues depuis cette session. Le cas a été reproduit sur une base isolée à partir de la description.
- Les déplacements en série (« et les suivantes », « toute la série ») mettent Google à jour mais n'envoient pas d'email aux clients. Pour mémoire, les emails ne partent toujours pas tant que le domaine n'est pas vérifié chez Resend.
- Une semaine par an environ (mars et fin octobre), 21h Bruxelles sort des horaires Miami (09:00-16:00 heure de Miami) et n'est pas proposé. C'est le comportement voulu depuis le 13/11.
- Tests d'intégration : ils exigent `TEST_PG` (PostgreSQL local, jamais Supabase).
